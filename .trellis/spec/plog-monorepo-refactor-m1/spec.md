## 2. 项目概述

### 2.1 项目背景

Plog 是一个基于 PHP 的传统单体 CMS 系统,具备完整的博客管理功能、主题系统和插件系统。当前系统采用传统的 PHP 单体架构,所有功能耦合在一个代码库中,存在以下问题:

- **架构耦合**: 前后端代码混合,难以独立开发和部署
- **扩展性受限**: 插件和主题系统缺乏标准化接口
- **开发效率低**: 缺乏现代开发工具链支持
- **维护成本高**: 单体架构导致代码维护困难

### 2.2 重构目标

将 Plog 从传统 PHP 单体应用重构为现代化的 Monorepo 架构,实现:

1. **前后端分离**: 前端采用现代框架,后端提供 RESTful API
2. **Monorepo 管理**: 统一管理多个应用和共享包
3. **插件/主题一等公民**: 提供标准化的扩展机制
4. **Manifest 驱动**: 通过配置清单管理系统状态
5. **开发工具链**: 提供完整的开发、构建、测试工具

### 2.3 M1 阶段范围

M1 阶段聚焦于 **核心基础架构搭建**,具体包括:

- 创建 Monorepo 目录结构
- 初始化核心包 (core, db, auth, content)
- 搭建基础 API 服务 (admin-api)
- 配置开发工具链基础
- 迁移核心业务逻辑

### 2.4 系统范围定义

#### 2.4.1 功能范围

**包含功能:**
- Monorepo 项目结构初始化
- 核心包的基础框架搭建

- 用户认证基础模块
- 内容管理核心模型

**不包含功能:**

- 主题系统重构 (M3 阶段)
- 完整的开发工具链 (M4 阶段)
- 生产环境部署配置

#### 2.4.2 技术边界

**技术栈约束:**
- 后端语言: PHP 7.4+
- 包管理: Composer
- Monorepo 工具: 待定 (考虑使用 symfony/flex 或自定义脚本)
- API 规范: RESTful API
- 数据库: MySQL 5.6+
- 前端框架: 待定 (M2 阶段确定)

**兼容性要求:**
- 保持与现有数据库结构的兼容性
- 支持平滑迁移,不破坏现有功能
- 提供迁移脚本和回滚机制

## 3. 需求规格

### 3.1 Monorepo 结构需求

#### REQ-STR-001: Monorepo 目录结构创建

**需求描述:**
系统应当提供符合 Monorepo 规范的目录结构,支持多应用、多包的统一管理。

**EARS 规格说明:**

**[Ubiquitous]** 系统应当包含以下顶层目录:
- `apps/` - 应用程序目录
- `packages/` - 共享包目录
- `plugins/` - 插件目录
- `themes/` - 主题目录
- `tooling/` - 开发工具目录
- `manifests/` - 配置清单目录

**[State-driven]** 当创建新的应用时,系统应当在 `apps/` 目录下创建对应的应用子目录,并包含标准的应用结构文件。

**[State-driven]** 当创建新的共享包时,系统应当在 `packages/` 目录下创建对应的包子目录,并包含 `composer.json`、`src/`、`tests/` 等标准文件。

**[Optional]** 如果项目需要自定义构建流程,系统应当支持在 `tooling/` 目录下配置自定义构建脚本。

**验收标准:**
- ✅ 目录结构符合 Monorepo 最佳实践
- ✅ 每个应用和包都有独立的 `composer.json`
- ✅ 根目录有统一的 `composer.json` 管理依赖
- ✅ 目录结构有清晰的文档说明

---

#### REQ-STR-002: 应用目录结构规范

**需求描述:**
系统应当为每个应用提供标准化的目录结构,确保应用间的结构一致性。

**EARS 规格说明:**

**[Ubiquitous]** 每个应用目录应当包含:
- `src/` - 源代码目录
- `config/` - 配置文件目录
- `public/` - 公共访问目录 (Web 入口)
- `routes/` - 路由定义目录
- `composer.json` - 应用依赖配置

**[State-driven]** 当应用需要 API 服务时,系统应当在应用目录下创建 `routes/api.php` 文件用于定义 API 路由。

**[Event-driven]** 当应用启动时,系统应当自动加载应用配置和路由定义。

**验收标准:**
- ✅ `apps/admin-api` 目录结构完整
- ✅ `apps/admin-web` 目录结构完整 (M2 阶段)
- ✅ `apps/site-runtime` 目录结构完整 (M2 阶段)
- ✅ 每个应用可独立运行和测试

---

#### REQ-STR-003: 共享包目录结构规范

**需求描述:**
系统应当为每个共享包提供标准化的目录结构,支持代码复用和独立测试。

**EARS 规格说明:**

**[Ubiquitous]** 每个共享包目录应当包含:
- `src/` - 源代码目录
- `tests/` - 测试代码目录
- `composer.json` - 包依赖配置

**[State-driven]** 当共享包需要提供配置时,系统应当在包目录下创建 `config/` 目录存放配置文件。

**[Optional]** 如果共享包需要提供公共资源文件,系统应当支持创建 `resources/` 目录。

**验收标准:**
- ✅ `packages/core` 目录结构完整

### 3.2 核心包需求

#### REQ-PKG-001: Core 包基础功能

**需求描述:**
Core 包应当提供系统核心功能,包括配置管理、日志记录、工具函数等基础能力。

**EARS 规格说明:**

**[Ubiquitous]** Core 包应当提供以下核心服务:
- 配置管理器 (Config Manager)
- 日志记录器 (Logger)
- 事件调度器 (Event Dispatcher)
- 服务容器 (Service Container)

**[State-driven]** 当系统初始化时,Core 包应当自动加载环境配置和系统配置。

**[Event-driven]** 当系统发生错误时,Core 包应当记录错误日志并触发错误事件。

**[Optional]** 如果需要自定义配置源,Core 包应当支持从数据库、文件、环境变量等多种来源加载配置。

**验收标准:**
- ✅ Config Manager 可加载 `.env` 和 PHP 配置文件
- ✅ Logger 支持 PSR-3 日志规范
- ✅ Event Dispatcher 支持事件监听和触发
- ✅ Service Container 支持依赖注入
- ✅ 所有核心服务有单元测试

---

#### REQ-PKG-002: DB 包数据库访问层

**需求描述:**
DB 包应当提供统一的数据库访问层,支持多种数据库操作和查询构建。

**EARS 规格说明:**

**[Ubiquitous]** DB 包应当提供以下数据库服务:
- 数据库连接管理器 (Connection Manager)
- 查询构建器 (Query Builder)
- 模型基类 (Model Base Class)
- 数据库迁移工具 (Migration Tool)

**[State-driven]** 当创建数据库连接时,DB 包应当支持配置连接池、读写分离等高级特性。

**[Event-driven]** 当执行数据库查询时,DB 包应当记录慢查询日志 (超过配置阈值)。

**[Optional]** 如果需要使用事务,DB 包应当提供事务管理器支持事务的开启、提交和回滚。

**验收标准:**
- ✅ 支持 MySQL 数据库连接
- ✅ Query Builder 支持链式调用
- ✅ Model 基类支持 CRUD 操作
- ✅ 迁移工具可执行数据库迁移
- ✅ 保持与现有数据库结构的兼容性

---

#### REQ-PKG-003: Auth 包用户认证模块

**需求描述:**
Auth 包应当提供用户认证和授权功能,支持多种认证方式和权限管理。

**EARS 规格说明:**

**[Ubiquitous]** Auth 包应当提供以下认证服务:
- 用户认证器 (Authenticator)
- 会话管理器 (Session Manager)
- 密码加密器 (Password Hasher)
- 权限检查器 (Permission Checker)

**[State-driven]** 当用户登录时,Auth 包应当验证用户凭证并创建用户会话。

**[Event-driven]** 当用户认证失败时,Auth 包应当记录失败日志并触发认证失败事件。

**[Optional]** 如果需要第三方认证,Auth 包应当支持扩展第三方认证提供者 (如 OAuth)。

**验收标准:**
- ✅ 支持用户名密码认证
- ✅ 密码加密使用 bcrypt 或 argon2
- ✅ 会话管理支持 PHP Session
- ✅ 权限检查支持角色和权限双重验证
- ✅ 兼容现有用户表结构

---

#### REQ-PKG-004: Content 包内容管理核心

**需求描述:**
Content 包应当提供内容管理的核心模型和业务逻辑,包括文章、分类、标签、评论等。

**EARS 规格说明:**

**[Ubiquitous]** Content 包应当提供以下内容模型:
- 文章模型 (Post Model)
- 分类模型 (Category Model)
- 标签模型 (Tag Model)
- 评论模型 (Comment Model)
- 媒体模型 (Media Model)

**[State-driven]** 当创建文章时,Content 包应当自动生成文章别名 (slug) 并设置创建时间。

**[Event-driven]** 当文章状态变更时,Content 包应当触发文章状态变更事件。

**[Optional]** 如果需要自定义内容类型,Content 包应当支持注册自定义内容类型。

**验收标准:**
- ✅ 所有模型支持 CRUD 操作
- ✅ 文章支持多种状态 (草稿、发布、归档)
- ✅ 分类和标签支持层级关系
- ✅ 评论支持审核机制
- ✅ 兼容现有数据库表结构

### 3.3 Admin API 需求

#### REQ-API-001: API 基础服务搭建

**需求描述:**
Admin API 应当提供后台管理的 RESTful API 接口,支持前端应用调用。

**EARS 规格说明:**

**[Ubiquitous]** Admin API 应当提供以下基础功能:
- API 路由定义
- 请求中间件 (认证、权限、日志)
- 响应格式化 (JSON)
- 错误处理机制

**[State-driven]** 当 API 接收到请求时,系统应当依次执行中间件链,验证请求合法性。

**[Event-driven]** 当 API 发生异常时,系统应当返回标准化的错误响应并记录异常日志。

**[Optional]** 如果需要 API 版本管理,系统应当支持通过 URL 前缀区分不同版本的 API。

**验收标准:**
- ✅ API 遵循 RESTful 规范
- ✅ 所有响应使用统一的 JSON 格式
- ✅ 错误响应包含错误码和错误信息
- ✅ 中间件可配置和扩展
- ✅ API 文档自动生成

---

#### REQ-API-002: 认证 API 接口

**需求描述:**
Admin API 应当提供用户认证相关的 API 接口。

**EARS 规格说明:**

**[Ubiquitous]** 系统应当提供以下认证 API:
- `POST /api/auth/login` - 用户登录
- `POST /api/auth/logout` - 用户登出
- `GET /api/auth/user` - 获取当前用户信息
- `POST /api/auth/refresh` - 刷新认证令牌

**[State-driven]** 当用户登录成功时,系统应当返回用户信息和认证令牌。

**[Event-driven]** 当认证令牌过期时,系统应当返回 401 状态码并提示令牌过期。

**验收标准:**
- ✅ 登录接口验证用户凭证
- ✅ 登出接口清除用户会话
- ✅ 用户信息接口返回当前用户详情
- ✅ 令牌刷新接口生成新令牌

---

#### REQ-API-003: 内容管理 API 接口

**需求描述:**
Admin API 应当提供内容管理相关的 API 接口。

**EARS 规格说明:**

**[Ubiquitous]** 系统应当提供以下内容管理 API:
- `GET /api/posts` - 获取文章列表
- `GET /api/posts/{id}` - 获取文章详情
- `POST /api/posts` - 创建文章
- `PUT /api/posts/{id}` - 更新文章
- `DELETE /api/posts/{id}` - 删除文章

**[State-driven]** 当创建或更新文章时,系统应当验证文章数据的完整性和合法性。

**[Event-driven]** 当文章操作成功时,系统应当触发相应的事件 (创建、更新、删除)。

**[Optional]** 如果需要批量操作,系统应当支持批量创建、更新、删除文章。

**验收标准:**
- ✅ 文章列表支持分页和筛选
- ✅ 文章详情返回完整信息
- ✅ 创建和更新接口验证数据
- ✅ 删除接口支持软删除
- ✅ 所有接口需要认证和权限验证

## 4. 非功能性需求

### 4.1 性能需求

**[Ubiquitous]** 系统应当满足以下性能要求:
- API 响应时间 < 200ms (P95)
- 数据库查询优化,避免 N+1 查询
- 支持连接池和缓存机制

### 4.2 安全需求

**[Ubiquitous]** 系统应当满足以下安全要求:
- 所有 API 接口需要认证
- 敏感数据加密存储
- 防止 SQL 注入、XSS、CSRF 等攻击
- 定期更新依赖包修复安全漏洞

### 4.3 可维护性需求

**[Ubiquitous]** 系统应当满足以下可维护性要求:
- 代码遵循 PSR-12 编码规范
- 所有公共接口有文档注释
- 核心功能有单元测试覆盖
- 提供完整的开发文档

### 4.4 可扩展性需求

**[Ubiquitous]** 系统应当满足以下可扩展性要求:
- 支持水平扩展 (无状态设计)
- 支持插件和主题扩展
- 支持自定义内容类型
- 支持第三方服务集成
