## 2. 核心理念

### 2.1 重构哲学

**不是把 PHP 改成 Rust，而是把系统核心逐步"Rust 化"，PHP 最后只剩兼容层。**

这条路线的本质是：
- PHP 从"核心业务实现者"降级为"兼容壳"
- Rust 承担新核心业务逻辑
- 系统核心逐步迁移，兼容层逐渐退休

### 2.2 架构分层思想

```
┌─────────────────────────────────────────────────────────────┐
│                    三层架构分离                               │
├─────────────────────────────────────────────────────────────┤
│                                                               │
│  ┌─────────────────────────────────────────────────────┐   │
│  │                  开发态 (Development)                 │   │
│  │  - 源代码组织                                        │   │
│  │  - 构建工具链                                        │   │
│  │  - 测试框架                                          │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                               │
│  ┌─────────────────────────────────────────────────────┐   │
│  │                  构建态 (Build)                       │   │
│  │  - Rust 编译产物                                     │   │
│  │  - 前端构建产物                                      │   │
│  │  - 配置清单生成                                      │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                               │
│  ┌─────────────────────────────────────────────────────────────┐
│  │                  运行态 (Runtime)                            │   │
│  │  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐     │
│  │  │ Rust Core    │  │ PHP Compat   │  │ Frontend     │     │
│  │  │ (新核心)     │  │ (兼容壳)     │  │ (独立前端)   │     │
│  │  └──────────────┘  └──────────────┘  └──────────────┘     │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                               │
└─────────────────────────────────────────────────────────────┘
```

## 3. 职责划分

### 3.1 Rust 承担的新核心

| 模块 | 职责 | 优先级 |
|------|------|--------|
| **API 服务** | RESTful API 处理、路由、中间件 | P0 |
| **Auth** | 用户认证、权限校验、会话管理 | P0 |
| **Content Domain** | 内容模型、业务规则、数据验证 | P0 |
| **Plugin Metadata** | 插件清单解析、能力声明、注册表 | P1 |
| **Theme Manifest** | 主题清单、渲染管线抽象 | P1 |
| **Task / Queue** | 异步任务管理、队列处理 | P1 |
| **Search** | 全文搜索、索引管理 | P2 |
| **Cache** | 缓存策略、缓存失效 | P1 |

### 3.2 PHP 保留的兼容壳

| 模块 | 职责 | 退休时间 |
|------|------|----------|
| **/admin 旧页面** | 传统后台页面渲染 | Phase 4 |
| **老插件入口** | 兼容现有 PHP 插件执行 | Phase 3 |
| **老主题入口** | 兼容现有 PHP 主题模板 | Phase 3 |
| **历史 include/controller** | 遗留调用链兼容 | Phase 4 |
| **内容迁移兼容逻辑** | 迁移期间的数据兼容 | Phase 2 |

## 4. 分阶段迁移路线图

### Phase 1: 边界收敛 (0-2 个月)

**目标**: 不急着改语言，先把现有系统整理成稳定边界

#### 关键任务

1. **固定 admin-api 接口契约**
   - 梳理现有 API 端点
   - 定义 OpenAPI/Swagger 规范
   - 建立 API 版本管理策略

2. **抽象领域接口**
   - 用户模型接口
   - 权限模型接口
   - 内容模型接口
   - 插件模型接口
   - 主题模型接口

3. **明确三态分离**
   - 定义哪些是开发态
   - 定义哪些是构建态
   - 定义哪些是运行态

4. **补全 Manifest 与能力声明**
   - 插件 manifest.json
   - 主题 manifest.json
   - 能力声明规范

#### 交付物

- API 接口规范文档
- 领域模型接口定义
- Manifest 规范文档
- 三态分离设计文档

#### 验收标准

- [ ] 所有 API 端点有明确的接口契约
- [ ] 核心领域模型有清晰的接口定义
- [ ] 插件和主题有标准化的 manifest 格式
- [ ] 三态分离边界清晰

---

### Phase 2: Rust 接管 admin-api (2-6 个月)

**目标**: 创建新的 Rust 服务，接管 admin-api 的新接口

#### 架构变更

```
┌─────────────────────────────────────────────────────────────┐
│                    Nginx 路由分流                            │
├─────────────────────────────────────────────────────────────┤
│                                                               │
│  /api/v2/*  ─────────────────►  Rust Core Service           │
│  /api/*     ─────────────────►  PHP admin-api               │
│  /admin     ─────────────────►  PHP 传统后台                │
│  /admin-web ─────────────────►  独立前端 (Vite)             │
│                                                               │
└─────────────────────────────────────────────────────────────┘
```

#### Rust 服务职责

- 新版 API 端点
- 新增功能
- 高价值、规则清晰的领域逻辑
- 用户认证
- 权限校验
- 内容管理 API
- 插件管理 API
- 主题配置 API
- 文件上传/媒体元数据 API

#### 技术选型建议

| 组件 | 推荐方案 |
|------|----------|
| **Web 框架** | Actix-web / Axum |
| **ORM** | SeaORM / Diesel |
| **数据库** | MySQL (保持兼容) |
| **认证** | JWT + Session |
| **序列化** | serde |
| **日志** | tracing |
| **配置** | config-rs |

#### 交互协议

推荐使用 **HTTP/JSON**，原因：
- 符合现有 Web/CMS 系统架构
- 与现有 admin-web 前端无缝对接
- 调试和监控简单
- 团队学习成本低

不推荐 PHP-Rust FFI，原因：
- 调试困难
- 内存安全风险
- 部署复杂度高

#### 交付物

- Rust core-api 服务
- Nginx 路由配置
- API 文档
- 数据库访问层

#### 验收标准

- [ ] Rust 服务可独立运行
- [ ] Nginx 路由分流正常
- [ ] admin-web 可消费 Rust API
- [ ] 旧 PHP 后台不受影响

---

### Phase 3: 掏空 PHP (6-12 个月)

**目标**: 让 PHP 变薄，只做兼容入口

#### 架构演进

```
┌─────────────────────────────────────────────────────────────┐
│                    PHP 变薄策略                               │
├─────────────────────────────────────────────────────────────┤
│                                                               │
│  PHP 只做:                                                    │
│  ├── 兼容入口 (接收请求，转发 Rust)                          │
│  ├── 老插件执行 (兼容层)                                     │
│  ├── 老主题渲染 (兼容层)                                     │
│  └── 历史路由兼容                                             │
│                                                               │
│  Rust 做:                                                     │
│  ├── 真实业务规则                                             │
│  ├── 数据写入                                                 │
│  ├── 认证授权                                                 │
│  └── 任务调度                                                 │
│                                                               │
└─────────────────────────────────────────────────────────────┘
```

#### 关键策略

1. **PHP → Rust 调用方式**
   - HTTP/JSON (推荐)
   - gRPC (如果团队能接受)
   - 消息队列 (异步任务)

2. **数据写入规则**
   - 尽量统一到 Rust
   - 共享数据库但禁止双边随意写
   - 建立数据所有权边界

3. **插件兼容策略**
   - 保留 PHP 插件执行环境
   - 新插件优先 Rust 实现
   - 提供 PHP-Rust 插件桥接

4. **主题兼容策略**
   - 保留 PHP 模板渲染
   - 新主题支持 Rust 模板引擎
   - 渲染管线可插拔

#### 交付物

- PHP 兼容层框架
- PHP-Rust 桥接服务
- 插件迁移工具
- 主题迁移工具

#### 验收标准

- [ ] PHP 代码量减少 60%+
- [ ] 核心业务逻辑在 Rust
- [ ] 老插件仍可运行
- [ ] 老主题仍可渲染

---

### Phase 4: 逐步退休 /admin (12-18 个月)

**目标**: 等 admin-web 覆盖率足够高，逐模块下线旧 PHP 页面

#### 模块退休顺序

| 顺序 | 模块 | 依赖条件 |
|------|------|----------|
| 1 | 用户与角色 | admin-web 用户管理完成 |
| 2 | 内容管理 | admin-web 文章管理完成 |
| 3 | 菜单/导航 | admin-web 菜单管理完成 |
| 4 | 插件管理 | admin-web 插件管理完成 |
| 5 | 主题配置 | admin-web 主题配置完成 |
| 6 | 系统设置 | admin-web 设置页面完成 |

#### 退休策略

- 新功能只进 admin-web
- 老功能留在 /admin
- /admin 逐页退休，不是整体重写
- 每个模块退休前需验收

#### 最终架构

│                                                               │

│  │ Rust Core    │  │ admin-web    │  │ Frontend     │     │
│  │ (主服务)     │  │ (管理后台)   │  │ (前台渲染)   │     │
│  └──────────────┘  └──────────────┘  └──────────────┘     │
│         │                  │                  │              │
│         └──────────────────┴──────────────────┘              │
│                            │                                  │

#### 交付物

## 6. 风险评估与应对

### 6.1 技术风险

| 风险项 | 影响程度 | 发生概率 | 应对措施 |
|--------|---------|---------|---------|
| Rust 团队技能不足 | 高 | 中 | 培训 + 小规模试点 |
| 数据库迁移失败 | 高 | 低 | 完整备份 + 回滚方案 |
| 性能回退 | 中 | 中 | 性能基准测试 + 监控 |
| 兼容性问题 | 高 | 中 | 充分测试 + 灰度发布 |

### 6.2 业务风险

| 风险项 | 影响程度 | 发生概率 | 应对措施 |
|--------|---------|---------|---------|
| 迁移期间服务中断 | 高 | 低 | 蓝绿部署 + 回滚能力 |
| 老插件/主题失效 | 高 | 中 | 兼容层保证 + 迁移工具 |
| 开发周期延长 | 中 | 中 | 分阶段交付 + MVP 思维 |
| 团队抵触 | 中 | 中 | 渐进式迁移 + 培训支持 |

### 6.3 关键风险应对

#### 风险: 老插件/主题失效

**应对策略**:
1. 保留完整的 PHP 执行环境
2. 提供 PHP-Rust 桥接层
3. 提供迁移工具和文档
4. 给予充足的迁移时间窗口

#### 风险: 数据一致性

**应对策略**:
1. 建立数据所有权边界
2. 双写期间增加一致性检查
3. 定期数据校验任务
4. 完善的监控和告警

## 9. 决策记录

### 9.1 为什么选择 HTTP/JSON 而非 FFI

**决策**: PHP 和 Rust 之间使用 HTTP/JSON 通信

**原因**:
1. 符合现有 Web/CMS 架构模式
2. 调试和监控简单
3. 团队学习成本低
4. 部署独立，互不影响
5. 便于水平扩展

### 9.2 为什么选择 Axum 而非 Actix-web

**决策**: 推荐使用 Axum 作为 Rust Web 框架

**原因**:
1. 基于 tokio/tower 生态
2. 更好的类型安全
3. 中间件系统灵活
4. 社区活跃度高

### 9.3 为什么选择 SeaORM 而非 Diesel

**决策**: 推荐使用 SeaORM 作为 ORM

**原因**:
1. 异步支持好
2. 实体关系定义清晰
3. 迁移工具完善
4. 与 Axum 集成良好
