# Plog CMS API 版本管理策略

## 概述

本文档定义 Plog CMS API 的版本管理策略，确保在 PHP → Rust 迁移过程中 API 的平滑过渡。

**最后更新**: 2026-03-29
**版本**: v1.0.0

---

## 版本号规范

### 格式

```
v{major}.{minor}.{patch}
```

- **major**: 不兼容的 API 变更
- **minor**: 向后兼容的功能性新增
- **patch**: 向后兼容的问题修正

### URL 版本

API 版本通过 URL 路径标识：

```
/api/v1/posts
/api/v2/posts
/api/v3/posts
```

## 版本生命周期

```
┌─────────────────────────────────────────────────────────────┐
│                    版本生命周期                               │
├─────────────────────────────────────────────────────────────┤
│                                                               │
│  开发中 ──► 活跃 ──► 维护 ──► 废弃 ──► 下线                 │
│  (dev)    (active) (maintained) (deprecated) (sunset)       │
│                                                               │
└─────────────────────────────────────────────────────────────┘
```

### 阶段说明

| 阶段 | 说明 | 支持周期 |
|------|------|----------|
| 开发中 | 新版本开发阶段 | - |
| 活跃 | 当前推荐使用的版本 | 无限期 |
| 维护 | 只修复安全问题和严重 Bug | 6 个月 |
| 废弃 | 发布废弃通知，建议迁移 | 3 个月 |
| 下线 | 不再可用 | - |

## 版本规划

### v1 (PHP 原有 API)

- **状态**: 维护
- **开始时间**: 2024-01-01
- **废弃时间**: Phase 3 结束
- **下线时间**: Phase 4 结束
- **说明**: 现有 PHP 实现的 API

### v2 (Rust 新 API)

- **状态**: 开发中
- **开始时间**: Phase 2 开始
- **目标**: 接管 v1 的所有功能
- **说明**: Rust 实现的新 API

### v3 (未来扩展)

- **状态**: 规划中
- **说明**: 预留未来扩展

## 迁移策略

### Phase 1-2: v1 和 v2 并行

```
/api/v1/* ──► PHP (维护模式)
/api/v2/* ──► Rust (开发模式)
```

### Phase 3: v2 为主，v1 兼容

```
/api/v1/* ──► PHP → Rust (代理模式)
/api/v2/* ──► Rust (活跃模式)
```

### Phase 4: v1 下线，v2 升级

```
/api/*    ──► Rust (活跃模式)
/api/v1/* ──► 410 Gone
```

## 版本废弃通知

### HTTP 响应头

废弃版本的 API 响应应包含以下头部：

```http
Deprecation: true
Sunset: Sat, 01 Jan 2027 00:00:00 GMT
Link: </api/v2/posts>; rel="successor-version"
```

### 响应体

```json
{
  "success": true,
  "data": {},
  "meta": {
    "deprecated": true,
    "sunset": "2027-01-01",
    "successor": "/api/v2/posts",
    "message": "此 API 版本已废弃，请迁移到 v2"
  }
}
```

## 兼容性保证

### 向后兼容规则

1. **不删除已有字段**
2. **不改变字段类型**
3. **不改变字段语义**
4. **不增加必填字段**

### 破坏性变更

以下变更需要升级 major 版本：

1. 删除 API 端点
2. 删除响应字段
3. 改变字段类型
4. 改变认证方式
5. 改变错误码

## 客户端迁移指南

### 1. 检测版本

```http
GET /api/v1/posts
```

响应头包含版本信息：

```http
X-API-Version: 1.0.0
X-API-Deprecated: true
X-API-Sunset: 2027-01-01
```

### 2. 迁移步骤

1. 检查当前使用的 API 版本
2. 阅读新版本的变更日志
3. 更新 API 调用路径
4. 测试所有 API 调用
5. 部署更新

### 3. 迁移工具

提供 CLI 工具帮助迁移：

```bash
# 检查 API 使用情况
plog api:check --version v1

# 生成迁移报告
plog api:migrate --from v1 --to v2
```

## 版本发布流程

### 1. 开发阶段

- 在 `v{version}-dev` 分支开发
- 定期合并到 `main` 分支

### 2. 测试阶段

- 部署到测试环境
- 运行集成测试
- 性能测试

### 3. 发布阶段

- 创建版本标签
- 更新文档
- 发布公告

### 4. 监控阶段

- 监控错误率
- 监控性能
- 收集反馈
